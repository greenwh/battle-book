## Restart Prompt
 
Use this exact prompt when starting a new Battle Book session:
 
> *“I’m Bill, working on the Battle Book. There are now two synced sites: **battle-book** (pha Ghosts, full branding) and **soa-battle-book** (SOA, stripped landing image + alliance/personal names). Live sites — pha: <https://greenwh.github.io/battle-book/> · SOA: <https://greenwh.github.io/soa-battle-book/> — fetch whichever book we’re working on, follow its MANIFEST.md link to see current deployed state, then read the battle-book continuity doc in project files. Content is identical across both sites; only branding differs. Ask me what we’re working on today.”*
 
**The URL in that prompt is load-bearing, not decoration.** `web_fetch` can only reach a URL that appeared in a prior tool result *or in one of Bill’s messages*. At the start of a cold session there are no prior tool results, and this small repo does not surface in web search. So the homepage URL **must arrive in Bill’s message** — pasting the restart prompt (which now carries both the pha and SOA URLs) is what seeds it into the whitelist. The whitelist is **per-URL**: seeding the pha homepage does not make the SOA homepage fetchable, and vice versa — so fetch the URL for whichever book you need to check (both are in the prompt). Once a homepage is fetched, its “Recently updated” section links to that site’s MANIFEST.md, which chains the rest. If Bill starts a session without the URL, ask him to paste the relevant site URL before trying to fetch anything.

## Session-Start Protocol (Do This Every Time)
 
**Step 1: Fetch the homepage.**
 
```
https://greenwh.github.io/battle-book/
```
 
This only works if the URL is already seeded — i.e. Bill pasted it this session (the Restart Prompt does this) or a prior fetch returned it. It is **not** automatically whitelisted on a cold start, despite what older versions of this doc claimed. If the fetch returns a permissions/whitelist error (`URL was not in any prior search or fetch result`), the fix is to have Bill paste the URL, not to retry. Do **not** rely on web search to find it — this repo does not index reliably.
 
Fetching the homepage confirms the site is reachable and, more importantly, seeds the MANIFEST.md link for Step 2.
 
**Step 2: Follow the manifest link from “Recently updated” on the homepage to:**
 
```
https://greenwh.github.io/battle-book/MANIFEST.md
```
 
The manifest lists every deployed page, the current sidebar config, and recent commit history. Auto-regenerated by GitHub Actions on every push to main.
 
**Step 3: Note the manifest’s `Last updated` timestamp.** Should be very recent (within hours, or at most a day, of the last commit).
 
**This is the only reliable way to know what’s actually live.** Project knowledge is a snapshot. The changelog can be aspirational. The live site can lag the repo by minutes. The manifest is the single source of truth.

## Dual-Site Operation (pha + SOA)
 
The Battle Book is deployed as **two synced sites** from two repos:
 
- **`battle-book`** — pha Ghosts. Full branding. Live: <https://greenwh.github.io/battle-book/>
- **`soa-battle-book`** — SOA clone. Live: <https://greenwh.github.io/soa-battle-book/>
**What's identical (everything that matters for content):** every page, the sidebar structure, all strategy / event / combat data. Content is alliance-agnostic, so the same files go into both repos byte-for-byte.
 
**What differs (the only divergence):** the landing-page hero image, and the alliance/personal-name strings stripped from the SOA copy. These are a small, fixed **do-not-touch** set that content work never modifies. Every handoff names them explicitly so Claude Code leaves them alone.
 
**Deploy model:** Claude Code is launched from the parent folder **above both repos** and updates **both on every change** — content, sidebar, and each repo's own MANIFEST (regenerated independently; each served at its own URL). Do not share or copy one manifest into the other. Internal and asset links are written **root-absolute** (e.g. `/fc-era-upgrade-costs.csv`); VitePress prepends each repo's own `base` (`/battle-book/` vs `/soa-battle-book/`) at build, so the same markdown resolves correctly in each site. **Never hardcode one repo's base path into the other.**
 
**Handoff pattern:** loop the same operation over both repos (`for REPO in battle-book soa-battle-book; do …`), confirm shared anchors exist in each before editing, and end with a per-repo post-deploy check (including: for SOA, confirm links resolve under the SOA base, not the pha base).
 
**Chat-side bootstrap:** only the site whose URL Bill pasted this session is fetchable (per-URL whitelist — see Restart Prompt). Both URLs live in the prompt, so either book can be checked. Both are kept in sync, so checking one usually reflects the other — but verify the specific site if a change might not have reached it yet.

## What The Battle Book Is
 
A public Whiteout Survival reference site, built by Bill (pha Ghosts R4, State 4104) for his multinational academy alliance and the broader community. The audience extends well beyond the alliance — links get shared, screenshots float around, players from other servers reference it.
 
**Design principles:**
 
1. **Alliance-agnostic content.** No Bill-specific roster examples, no State 4104 tactical references, no “Waldo’s loadout.” The content has to work for any reader.
1. **Translation-friendly.** Written for tools like Google Translate to handle cleanly — short sentences, plain vocabulary, no idioms when avoidable.
1. **Novice-accessible.** Assumes the reader knows the game but not necessarily the meta. Explains terms on first use. Cross-references the glossary.
1. **Fact-checked.** Every page footer lists sources (wiki, community guides, official posts). Conflicting community claims get presented honestly, not flattened to a single “correct” answer.
1. **Mobile-first.** Bill plays on mobile and reviews edits on mobile. Layouts must work on a 380px viewport.
1. **No emojis in content** (frontmatter or callouts), no promotional language, no recruitment pitches.
**What it isn’t:** a news feed (patches get baked into relevant guides, not announced separately), a recruitment site, or an authoritative source (every page says “verify against in-game changes”).

## Content Conventions
 
### Frontmatter (every content page)
 
```yaml
---
title: Page Title
description: One sentence — appears in search and SEO.
---
```
 
### Page structure (the established template)
 
1. Frontmatter
1. `# Heading` (matches title)
1. `::: info` callout — “Quick take” / at-a-glance
1. Mechanics (How It Works)
1. Phase-by-phase or section-by-section content
1. Strategy by Player Type (where relevant — F2P / minimal / heavy spend)
1. Common Mistakes
1. Quick Reference card / summary table
1. Related Guides (internal links)
1. Footer: `*Last verified: Month YYYY · Sources: [list]*`
### Callout syntax (VitePress-native)
 
Use these directly in markdown:
 
```
::: info
Quick take
:::
 
::: tip
Helpful side note
:::
 
::: warning
Watch out for this
:::
 
::: danger
Hard rule, do not break
:::
```
 
(There is also a `<Callout>` Vue component — see CLAUDE.md — but the `:::` syntax is what most pages use.)
 
### Voice rules
 
- Lead with the answer, not the buildup
- “You” voice (addressing the reader directly)
- Active voice
- Tables for comparison data (better than prose for ratios, costs, decision trees)
- Don’t use emojis
- Don’t say “the developers have indicated” — just state what’s known and cite

## The Chat ↔ Claude Code Workflow
 
**Chat Claude writes content. Claude Code deploys it.** That split is intentional and important.
 
### What stays in chat
 
- Researching topics (web search, fact-checking, community guides)
- Drafting markdown content
- Designing page structure
- Writing the handoff document
- Bundling content into a deployment shell script
### What goes to Claude Code
 
- Running the deployment shell script
- Editing `docs/.vitepress/config.ts` (sidebar/nav)
- Updating `docs/reference/glossary.md` and `docs/reference/changelog.md`
- Editing `docs/index.md` (homepage)
- Running `npm run build` to verify
- Git commit and push
### The handoff document pattern
 
Standard structure for any handoff:
 
```
# Claude Code Handoff — [Topic]
 
**Date / Author / Purpose**
 
## What Already Got Done (if recovery)
## What's Still Pending
 
## Phase 0 — State Verification
  [shell commands to verify current state]
  [stop for Bill's go-ahead]
 
## Phase 1 — [first work step]
## Phase 2 — [next step]
...
 
## Phase N — Commit and Push
## Phase N+1 — Post-Deploy Verification
 
## Notes for Bill (optional)
```
 
**Critical:** every handoff needs **Phase 0 verification** before any changes. Don’t trust the previous state — confirm it.
 
### The deployment shell script pattern
 
For content additions, bundle markdown files into a single shell script using heredocs:
 
```bash
#!/bin/bash
set -e
 
mkdir -p docs/some-section
 
cat > docs/some-section/page-name.md << 'EOF_UNIQUE_DELIMITER'
[markdown content]
EOF_UNIQUE_DELIMITER
 
# repeat for each file
 
echo "Complete: N files written"
```
 
Use a **unique delimiter per file** (e.g., `EOF_PAGE_NAME`) so nothing collides with content. The `set -e` ensures any failure stops the script.
 
**Always test the script** in `/tmp/test-repo` before delivering — run it, diff outputs against source files, confirm byte-identical.

## The Sync Mechanism (MANIFEST.md)
 
**Location:** `docs/public/MANIFEST.md` in the repo, served at `https://greenwh.github.io/battle-book/MANIFEST.md`.
 
**How it’s maintained:**
 
- `scripts/generate-manifest.sh` walks the docs/ tree and writes a fresh manifest
- `.github/workflows/update-manifest.yml` runs the script on every push to main that touches `docs/`
- The workflow commits the regenerated manifest with `[skip manifest]` in the message (prevents recursive triggers)
**What’s in it:**
 
- Last updated timestamp
- Last commit hash
- Full deployed file listing by section
- Current sidebar config (excerpt from config.ts)
- Recent commit history (last 10)
**What’s NOT in it:**
 
- Content of pages (just their existence as files)
- Glossary terms, changelog entries, or page text
**Implication:** the manifest tells you what files exist, not what’s in them. **For content claims, fetch the actual page and grep.** See “Lessons Learned” below.
 
### Why the manifest matters
 
The web_fetch tool requires URLs to come from prior search/fetch results or user messages. Bill pasting URLs in chat counts; me writing them in past output does not.
 
The manifest sits on the same domain as the live site (`greenwh.github.io/battle-book`). Once the homepage is fetched, its “Recently updated” section contains a real hyperlink to MANIFEST.md, which seeds that URL so it can be fetched in turn. But the homepage itself has to be reachable first, and that depends on the URL being in Bill’s message. So the real chain is:
 
```
Bill pastes URL (restart prompt) → fetch homepage → discover manifest link → fetch manifest → know deployed state
```
 
The first arrow is the one that was missing from earlier versions of this doc. Without it, the chain never starts on a cold session. This is the **only** reliable way to bootstrap state knowledge in a fresh session.

## Lessons Learned (Real Incidents)
 
### Incident 1: Partial deploy went undetected
 
A combined handoff did the content portion but skipped Phases 1–3 (sync infrastructure). Chat Claude assumed everything deployed because the chat session ended with no error reports. Took a verification cycle to discover the homepage hadn’t been updated and the manifest hadn’t moved to its new path.
 
**Fix:** every handoff must end with **Phase N+1 — Post-Deploy Verification** that fetches specific URLs and confirms specific text is present. “Build succeeded” is not the same as “the right things deployed.”
 
### Incident 2: Manifest claims about content
 
Chat Claude said “the glossary’s 12 new terms never got added” based on inference (assumed the same handoff that failed on homepage also failed on glossary). The claim happened to be correct but was unverified — never fetched the live glossary page to check.
 
**Fix:** for any claim about page content (not file existence), fetch the page and verify the text. The manifest is for file presence; page fetches are for content.
 
### Incident 3: Whitelist constraint underestimated
 
Chat Claude assumed once a domain was whitelisted via one URL, all URLs on that domain were accessible. Wrong — the whitelist is per-URL. Discovery has to happen through actual hyperlinks in fetched pages.
 
**Fix:** put discoverable links to everything important on the homepage. Don’t rely on guessing URLs.
 
### Incident 4: Bundled handoff phases got skipped
 
When too many phases stack in one handoff, Claude Code can drop steps silently. The Battle Reports + sync fixes combined handoff dropped the homepage update and glossary/changelog updates while completing the content work.
 
**Fix:** for handoffs over ~6 phases, consider splitting. Or front-load the most critical items (sync infra before content). Don’t assume “Claude Code will get to it” — order matters.
 
### Incident 5: The “homepage is always whitelisted” myth (the recurring manifest failure)
 
For weeks, fetching the manifest at session start failed intermittently and nobody could explain why. Root cause: the session where the sync mechanism was “solved” was a **warm** session — Bill had already pasted the live URL earlier in that same conversation, so the homepage was already in the whitelist when the chain was tested. Chat Claude concluded “Fetch homepage (always allowed)” and wrote that into this doc’s Session-Start Protocol. Every **cold** session afterward had no prior fetch result and no pasted URL, so the homepage fetch was rejected with `URL was not in any prior search or fetch result`. Search couldn’t recover it because the repo doesn’t index.
 
**Fix:** the live URL now lives **in the Restart Prompt**, so pasting the prompt seeds the whitelist on a cold start. The homepage is never “automatically” fetchable — it is fetchable *because Bill’s message carried the URL*. Never restore the “always whitelisted” phrasing. (Verified end-to-end on June 7, 2026: pasted URL → homepage → manifest, clean.)
 
### Incident 6: Stale "pending" labels trusted over live repo state
 
The FC cost CSV — and this session's Server Timeline + Hero Roster — were recorded here as "pending / not deployed" while actually **live in both repos**. Bill caught the disconnect ("you're telling me things are not deployed that are"). Root cause: the doc tracks *intent*, and "pending" labels were never reconciled to live state after Claude Code deployed; chat Claude then repeated the inherited "pending" claim without checking — the same inference-over-verification trap as Incident 2. The sync itself was fine the whole time.
 
**Fix:** reconcile against the repo, not the doc. `raw.githubusercontent.com/greenwh/<repo>/main/<path>` is reachable from bash with **no per-URL whitelist**, so any file's existence and content can be checked freely — including at session start, to clear any "pending" entries before trusting them. Treat doc "pending" labels as *unverified until checked*. Paired with the "handoff = deployed" rule (Approach Patterns), this keeps the doc honest.

## Approach Patterns (How Bill Likes to Work)
 
- **Raw data → analysis with math shown → clear recommendation.** Bill provides screenshots, standings, CSVs. He expects the response to walk the math, not just state a conclusion.
- **Concise corrections.** When Bill says “actually, X is wrong,” update the model and move on. Don’t over-apologize.
- **Push back on complexity.** Bill prefers minimal-move solutions to over-engineered restructures. Default to the simplest workable approach.
- **Use `ask_user_input_v0` for genuine decisions only.** Three-question max. Bill answers via mobile taps. Skip it when the right answer is obvious from context.
- **Show the file before delivering it.** Use `view` on what you wrote to confirm it’s right, then `present_files`. Don’t dump deliverables blind.
- **Tone:** direct, practical, no flattery, no preamble. Bill knows the game and the system — explain to a peer, not a beginner.
- **Assume handoff = deployed.** When a Claude Code handoff is delivered to Bill, treat the changes as **live** and update continuity/state in the same session — don't wait for a post-deploy confirmation to record it (Bill's standing instruction, June 26 2026). The manifest remains the source of truth if byte-level verification is ever needed, but day-to-day, handoff means done. (Note: this relaxes the older "verify before claiming deployed" stance from the Incident Log — that history is kept as cautionary background, but Bill has explicitly chosen the assume-deployed default.)
